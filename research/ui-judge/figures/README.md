## Notes on each

**Figure 1** is laid out so that at `dpi=200` every panel is exactly 320×170 px,
the panel's native resolution, so the frames are never resampled — matplotlib
draws them with `interpolation="nearest"`. Rows are grouped by tier and sorted
by `mean9` descending within tier, so the ladder reads top-to-bottom inside each
band. The three orange callouts are hand-picked in the `calls` dict; change them
there if the argument changes. The right-hand bar is `mean9` on a 1–7 scale.

**Figure 2** takes both compile gates from `gate1_compile.csv` and
`gate1_repair.csv`. The right panel is derived, not stored: it counts
`passes_used` among builds where `compiled == False` and
`deployed_compiled == True`.

**Figure 3** panel (a) recomputes the cross-tier pairwise win rate from
`judge_pairwise.csv` rather than reading `analysis.txt`, and drops
position-inconsistent pairs (a judge that flipped when A and B were swapped) as
ties rather than resolving them — hence n = 1,842 of 2,941 total comparisons.
The α values in panel (c) are transcribed from `analysis.txt`, which is the only
place they are computed.

**Figure 4** joins to two external sources, both in `A:\bridge\`:

- latency from `lith_provider_latency.xlsx`, `latency` sheet, `mean (s)` column;
- list prices from `lith_provider_cost.png`, which is the **only** place the
  full resolved price matrix is written down.

Both are hard-coded in `make_figures.py` as `LAT` and `PRICE` rather than parsed,
so that the figure cannot silently change if those files are regenerated. If
either source is refreshed, update the dicts deliberately.

## Two data caveats that affect Figure 4

1. **`analysis.txt` says quality-per-dollar was "left undone rather than
   guessed" because the prices "are not written down anywhere in the existing
   artefacts."** That is no longer true — they are charted in
   `lith_provider_cost.png` (checked live 2026-08-10), and are now transcribed
   into `PRICE`. Panel (b) is the analysis that file declined to do.

2. **`lith_provider_latency.md` is stale relative to `lith_provider_latency.xlsx`.**
   The prose describes an eight-model run (`claude-sonnet-5` stdev 1.78 s,
   `deepseek-chat` 4.15 s mean, openai "1–1.5 s range"). The spreadsheet, written
   37 minutes later, holds an eleven-model run whose numbers disagree sharply —
   `claude-sonnet-5` at 39.087 s mean / 49.882 s stdev, `deepseek-v4-flash` at
   73.968 s. **The figures use the spreadsheet.** Do not quote the `.md` prose in
   the cost study without re-checking it against the `raw` sheet.

Separately, the `gpt-5.5` row (0.193 s mean, 0.012 s stdev, 9/9 ok) is not a
credible build-turn latency and is annotated as such in the figure. It needs
re-measuring before it supports any quality-per-second claim.
